# 测试需求评审 Agent 设计

## 1. 背景与目标

测试人员收到需求文档后，需要判断需求是否足以支持手动测试和自动化测试，并把缺失信息准确反馈给需求人员。首版产品以 VS Code GitHub Copilot Chat 自定义 Agent 为入口，分析用户指定的 PDF，生成可追溯的需求评审结果。

首版目标：

- 解析包含正文和表格的文本型 PDF，不包含 OCR。
- 将文档拆分为带原文证据的原子需求。
- 识别可测试性缺口，以及手动测试和自动化测试分别缺失的信息。
- 为需求建议适用的正常、异常、边界、状态迁移和恢复等测试场景。
- 分别计算“需求可测试性得分”和“建议场景覆盖度”。
- 生成结构化 JSON、Markdown 和 Word 报告，并在 Copilot Chat 中展示摘要。
- 默认适配家电、嵌入式和 IoT 需求，同时允许增加领域规则包。
- 支持当前 Copilot 模型、公司批准的 API 或本地模型，且明确显示数据去向。
- 通过仓库内的 Agent 和 MCP 配置让其他团队成员复用。

首版不计算真实测试覆盖率。真实覆盖率必须在后续版本中引入现有测试用例或执行结果后才能计算。

## 2. 范围外事项

- 扫描件和图片 OCR。
- 上传现有测试用例并计算需求到用例的真实覆盖率。
- 自动生成可直接执行的测试代码。
- Web 页面、用户账户、远程文件存储和集中式任务管理。
- 多人同时编辑同一评审任务。
- 未经用户明确选择，将 PDF 或报告上传到额外的第三方服务。

## 3. 方案选择

采用“Copilot 自定义 Agent + 本地 Python MCP 分析引擎”。

纯提示词方案虽然更快，但 PDF 表格处理、结构化输出和评分难以稳定验证。先开发完整 Web/API 平台则会过早引入部署、认证、存储和运维。选定方案把交互留在 Copilot Chat，把解析、校验、评分和报告生成放入可测试的本地服务，并为未来 Web 页面保留同一应用服务接口。

核心原则是：模型提供带证据的语义判断，MCP 引擎负责结构校验和确定性评分。模型不能直接给出最终覆盖率数字。

## 4. 系统架构

### 4.1 Copilot 自定义 Agent

工作区 Agent 存放在 `.github/agents`，负责：

- 收集 PDF 路径、规则包和模型模式。
- 调用 MCP 工具执行解析、分析准备、校验、评分和报告生成。
- 在 Copilot 模式下完成语义分析，并按统一 Schema 返回结果给 MCP。
- 在 Chat 中展示摘要、关键阻塞项、产物路径和失败清单。
- 在执行前说明当前模型提供方及文档数据去向。

Agent 不实现 PDF 解析、分数计算或文档渲染。

### 4.2 Python MCP 分析引擎

本地 MCP 服务由以下独立组件组成：

- **PDF 提取器**：提取文本、标题层级、表格、页码和位置；检测加密、损坏及扫描页。
- **需求规范化器**：拆分原子需求、生成稳定 ID，并维护来源引用。
- **规则引擎**：加载规则包，确定每条需求适用的检查项和场景类别。
- **分析协调器**：组织统一的模型输入和输出协议；在外部或本地模型模式下调用模型适配器。
- **Schema 校验器**：拒绝缺少证据、字段错误或枚举值非法的模型输出。
- **评分器**：仅根据已校验的结构化结果和规则权重计算指标。
- **报告生成器**：从同一 JSON 事实源生成 Markdown 和 Word。
- **运行存储**：在独立目录保存中间结果、最终报告、失败信息和运行元数据。

这些组件通过 Python 应用服务组合。未来 Web API 只能调用该应用服务，不直接依赖 MCP 协议或 Copilot Agent。

### 4.3 规则包

规则包采用可版本化的结构化配置，首版提供家电、嵌入式和 IoT 默认规则。规则维度至少包括：

- 行为、输入、输出和验收标准。
- 前置条件、状态、状态迁移和并发行为。
- 边界值、非法输入、超时、重试和故障恢复。
- 设备、App、Cloud、BLE、Wi-Fi 及其他组件间依赖。
- 权限、安全、隐私、性能和兼容性。
- 自动化所需接口、数据准备、可观测状态、日志和复位能力。

规则包决定检查项是否适用及其权重，但不能修改分析结果 Schema。新增规则包无需修改报告生成器。

### 4.4 模型模式

所有模型模式共享同一分析协议：输入为原子需求、来源证据和适用规则；输出为符合 Schema 的判断、证据引用、置信度和建议问题。

- **Copilot 模式**：当前 Copilot 模型在 Agent 上下文中完成语义判断，MCP 负责后续校验和评分。MCP 不尝试从服务端反向调用当前 Copilot Chat 模型。
- **公司 API 模式**：MCP 通过模型适配器调用用户明确配置且公司允许的 API。
- **本地模型模式**：MCP 通过相同适配器接口调用本地推理服务。

切换模型不改变 PDF 提取、Schema、评分公式或报告格式。模型不可用时，系统停止语义分析并保留已完成的提取结果。

## 5. 数据流

1. 用户在 Copilot Chat 中选择 PDF、规则包和模型模式。
2. Agent 调用 MCP 创建独立运行目录并记录运行配置。
3. PDF 提取器校验文档，提取正文、标题、表格和来源位置。
4. 规范化器拆分原子需求；不能可靠拆分的内容标记为人工核对项。
5. 规则引擎为每条需求计算适用检查项和场景类别。
6. 选定模型逐条输出结构化分析结果。
7. Schema 校验器检查字段、枚举、证据引用和结果完整性；局部失败按限制重试。
8. 评分器计算逐条与整体指标。
9. 报告生成器从最终 JSON 生成 Markdown 和 Word。
10. Agent 展示摘要、重要问题、产物路径和任何未完成项。

每条原子需求必须保留稳定 ID、PDF 页码、章节、表格位置和原文片段。所有事实性结论必须引用这些来源；不能被原文支持的内容只能标为“建议”。

## 6. 分析结果模型

每条需求的结果至少包含：

- 需求 ID、规范化描述和来源引用。
- 适用规则及其权重。
- 已明确、缺失、不适用和需要人工确认的检查项。
- 缺口影响范围：手动测试、自动化测试或两者。
- 严重级别：阻塞、重要、一般。
- 建议测试场景及对应类别。
- 应向需求人员提出的问题。
- 结论类型：原文事实或分析建议。
- 置信度及模型给出的简短理由。

置信度用于提示人工复核优先级，不参与可测试性和场景覆盖度的计算。

## 7. 评分定义

### 7.1 需求可测试性得分

对单条需求，只统计规则引擎判定为适用的检查项。检查项状态为“已明确”时获得该项全部权重；“缺失”或“需要人工确认”不得分；“不适用”不进入分母。

$$
T_r = \frac{\sum_{i \in C_r} w_i \cdot complete_i}{\sum_{i \in C_r} w_i} \times 100
$$

其中 $C_r$ 为需求 $r$ 的适用检查项，$complete_i$ 只能为 $0$ 或 $1$。当不存在适用检查项时，该需求不参与整体平均，并必须标记为规则配置异常。

### 7.2 建议场景覆盖度

规则引擎先确定适用场景类别。某类别只有在结果包含可执行的测试思路并引用需求证据时才算已覆盖。

$$
S_r = \frac{|covered_r|}{|applicable_r|} \times 100
$$

该指标只表示建议测试设计对适用场景类别的覆盖程度，不表示现有用例覆盖率，也不表示测试执行覆盖率。报告标题、字段名和说明必须保留这一区分。

### 7.3 整体汇总

首版在没有需求优先级的情况下按需求等权平均，同时展示分布和逐条得分。系统不得猜测优先级。若 PDF 明确提供优先级，可以在明细中展示，但首版不改变整体权重。

## 8. 报告与语言

最终 JSON 是唯一事实源，Markdown 和 Word 均由它生成。三种产物必须具有相同的需求 ID、评分、缺口和证据。

报告包括：

- 执行摘要和文档处理状态。
- 两个指标的定义、整体结果和分布。
- 阻塞性缺口与需求人员待答问题。
- 逐条需求评审矩阵。
- 手动测试与自动化测试缺失信息的独立视图。
- 建议场景矩阵。
- 无法解析、无法确认或模型处理失败的条目。
- 工具、规则包、模型及生成时间等运行元数据。

报告正文和问题默认使用中文。协议名、接口名、状态名、技术术语以及 PDF 中的专业名词保留英文。原文证据始终保持原语言，不进行可能失真的强制翻译。

## 9. 错误处理与恢复

- 加密、损坏、纯扫描或无法解析的 PDF 在分析前失败，并报告原因和已知页码。
- 表格提取不确定时保留原始文本与位置，标记为“需人工核对”。
- 模型输出必须通过 JSON Schema。局部失败在固定次数内重试，之后进入失败清单。
- 单条需求失败不撤销其他需求的有效结果；报告必须显式展示未完成条目。
- 每个阶段写入可恢复的中间结果。再次运行时，只有输入文件哈希、规则版本、模型模式和 Schema 版本均匹配才可复用。
- Word 生成失败时仍保留 JSON 和 Markdown，并返回部分成功状态。
- 系统不得静默删除页面、表格、需求或失败结果。

## 10. 数据安全

- 每次运行前显示模型提供方和数据流向；外部 API 模式必须由用户显式选择。
- 密钥仅通过环境变量或 VS Code 安全输入获取，不写入仓库、示例配置、日志或报告。
- PDF、提取文本、中间文件和报告默认仅保存在本地运行目录中。
- 运行产物目录默认加入 Git 忽略，用户主动选择后才能共享报告。
- 日志避免记录完整需求正文和凭据，只记录需求 ID、阶段和错误摘要。
- 报告记录工具版本、规则包版本、Schema 版本、模型名称和生成时间，以支持审计和复现。
- MCP 工具遵循最小权限，只访问用户指定的输入文件和项目内运行目录。

## 11. 可迁移性

团队共享内容包括：

- `.github/agents` 中的工作区自定义 Agent。
- `.vscode/mcp.json` 中不含凭据的 MCP 启动配置。
- Python MCP 服务、规则包、Schema、模板和测试。
- 环境变量示例及 Windows 安装说明。

团队成员克隆仓库后安装固定版本依赖，即可在 VS Code 中发现 Agent 和 MCP 配置。使用者需要有效的 GitHub Copilot 权限；Copilot Business 或 Enterprise 环境还需要管理员允许 MCP。外部或本地模型依赖由对应适配器文档说明。

自定义 Agent 只是可迁移入口，核心评审能力不依赖某个用户的 VS Code Profile。未来 Web 页面、命令行或其他支持 MCP 的客户端可以复用同一分析引擎。

## 12. 测试策略

- **单元测试**：覆盖 PDF 文本和表格提取、规则加载、Schema 校验、评分、恢复判定及三种产物渲染。
- **确定性测试**：对固定 JSON 输入重复计算评分，结果必须完全一致。
- **模型契约测试**：所有模型适配器通过同一输入输出契约；默认使用假模型离线运行。
- **评估集测试**：使用中英混合的家电和 IoT 需求样本，检查缺口类别、证据位置和严重级别，不比较模型生成的具体措辞。
- **端到端测试**：通过 MCP 输入含正文和表格的 PDF，生成一致的 JSON、Markdown 和 Word。
- **故障测试**：覆盖加密、损坏、扫描 PDF，表格不确定，模型超时，非法模型输出和 Word 生成失败。
- **可迁移性测试**：在全新 Windows 环境执行安装、Agent 发现、MCP 启动和样例分析冒烟测试。

测试样本不得包含真实机密需求。评估集使用合成或经过批准且脱敏的内容。

## 13. 首版验收标准

首版完成需同时满足：

1. 团队成员可以从全新检出按文档启动 MCP，并在 Copilot Chat 选择需求评审 Agent。
2. 一份包含文本和表格的 PDF 能被拆分为可追溯的原子需求。
3. 每条事实性结论都链接到有效原文证据；无证据推断明确标为建议。
4. 报告分别展示手动测试和自动化测试缺失信息。
5. 两个指标按本设计公式计算、可解释、可复算，并明确声明不是真实测试覆盖率。
6. JSON、Markdown 和 Word 的需求 ID、评分、缺口和证据一致。
7. 中文报告保留英文技术术语和原始引用。
8. 无法解析的页面、表格和需求，以及模型失败条目均不会被隐藏。
9. 相同结构化输入产生相同评分和报告数据。
10. PDF 和运行产物默认只保存在本地，仓库中不包含凭据。

## 14. 后续演进

首版稳定后，按价值顺序考虑：

1. 上传现有测试用例，生成需求到用例的追踪矩阵和真实覆盖率。
2. 提供复用同一应用服务的简洁 Web 页面。
3. 对接 Jira、测试管理系统和代码仓库。
4. 在人工批准后生成测试用例草案及自动化候选项。
5. 增加 OCR、多文档关联分析、需求版本差异和回归影响分析。

每项演进独立设计，不能以首版的“建议场景覆盖度”替代真实用例或执行覆盖率。
